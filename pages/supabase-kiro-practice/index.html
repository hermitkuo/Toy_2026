01 · Architecture

先把責任邊界畫清楚

不要把 onboarding、steering、MCP 與 Hook 全塞進同一份 Prompt。那會形成不可維護的「超級指令」。

Power 套件

supabase-lab-power/ ├── POWER.md ├── mcp.json └── steering/ ├── database-setup.md ├── rls-policies.md ├── auth-nextjs.md ├── migrations.md └── realtime.md

安裝後的專案 Workspace

my-app/ ├── .kiro/ │ ├── hooks/ │ │ ├── supabase-sql-review.json │ │ └── supabase-stop-review.json │ └── steering/ ├── supabase/ │ ├── config.toml │ └── migrations/ └── package.json
判斷規則：Power 是可攜式能力包；Hook 是專案內事件自動化。Onboarding 寫在 POWER.md，並可要求 Agent 建議或建立 workspace hooks。
02 · Build sequence

最小可行建立順序

① 先定義能力邊界

只處理 Supabase database、Auth、RLS、Storage、Realtime 與 Edge Functions。不要擴張到所有後端框架。

② 建立 POWER.md

描述何時啟動、如何 onboarding、有哪些 MCP tools、什麼情況使用哪份 steering。

③ 拆 Multiple steering

每份文件只負責一個工作域，避免 RLS、Auth、Migration 規則互相污染。

④ 接上 MCP

讓 Agent 能讀取 hosted project 或 local stack，而不只是產生範例程式碼。

⑤ 生成 Workspace Hook

在 SQL save 或 Agent stop 時執行 lint、測試或語意審查。

⑥ 用情境驗收

以「新增多租戶資料表＋RLS」測試是否正確選取 steering、工具與安全檢查。

# Supabase Lab Power

## Onboarding

When first used in a workspace:

1. Inspect, but do not overwrite:
   - supabase/config.toml
   - package.json
   - .env.example
   - existing database migrations
   - .kiro/hooks/

2. Verify:
   - Supabase CLI
   - Docker, only when local development is requested
   - selected mode: hosted project or local stack

3. Security baseline:
   - never place real secrets in tracked files
   - service-role key is server-only
   - missing values are not silently replaced
   - destructive migrations require explicit disclosure

4. Recommend workspace hooks:
   - SQL migration review after save
   - final Supabase security review before agent stop

5. Report readiness:
   - CLI status
   - project mode
   - migration path
   - authentication pattern
   - RLS coverage
   - blockers

## Steering selection

Use the relevant workflow file only:
- database setup → steering/database-setup.md
- RLS or tenant isolation → steering/rls-policies.md
- Next.js authentication → steering/auth-nextjs.md
- schema changes → steering/migrations.md
- subscriptions or broadcast → steering/realtime.md

## Working rules

- Prefer versioned migrations over ad-hoc production edits.
- Treat RLS as part of schema design, not a final patch.
- Distinguish anon, authenticated and service-role privileges.
- Never claim security based only on successful UI behavior.

# Supabase RLS

Before creating a policy, identify:
- actor
- protected table
- tenant or ownership key
- permitted operation
- trusted claim source
- bypass role

Required checks:
1. Enable RLS on exposed tables.
2. Separate SELECT, INSERT, UPDATE and DELETE semantics.
3. Validate both USING and WITH CHECK.
4. Do not trust user-editable metadata for authorization.
5. Test cross-tenant denial, not only allowed access.
6. Report service-role bypass explicitly.
---
inclusion: fileMatch
fileMatchPattern:
  - "supabase/migrations/**/*.sql"

# Migration Safety

For every schema change:
- use a versioned migration
- identify lock and downtime risk
- identify data backfill strategy
- avoid adding NOT NULL before backfill
- review rollback feasibility
- disclose destructive operations
- regenerate application types when needed

Never use SELECT * in persistent views or application queries.

# Auth with Next.js

- Keep service-role credentials server-side.
- Separate browser and server client construction.
- Validate authorization at the database layer with RLS.
- Do not treat a hidden UI element as access control.
- Handle expired and missing sessions explicitly.
- Avoid logging tokens, cookies or personally identifiable data.

# Realtime

Before implementation, decide whether the use case requires:
- Postgres Changes
- Broadcast
- Presence

Review:
- channel naming
- authorization
- unsubscribe lifecycle
- duplicate events
- reconnect behavior
- optimistic update reconciliation
- data volume and fan-out risk
設計盲點：多份 steering 可以同時相關。避免重複寫共通規則；共通安全原則留在 POWER.md，專業細節才放各自 steering。
05 · MCP

把「知道 Supabase」升級為「能操作 Supabase」

mcp.json 示意

{
  "mcpServers": {
    "supabase": {
      "command": "npx",
      "args": [
        "-y",
        "@supabase/mcp-server-supabase"
      ]
    }
  }
}

何時值得使用 MCP

任務只用文字使用 MCP
產生 SQL 範例可非必要
檢查真實 schema不足必要
檢查 advisor / RLS不足必要
執行變更不可需工具＋權限控管
Not-to-do：不要把 access token、service-role key 或資料庫密碼直接寫入 Power repository。Power 可被分享；秘密必須由使用者端安全設定注入。
06 · Workspace Hooks

事件自動化落在 `.kiro/hooks/`

Kiro 1.0 使用 `.kiro/hooks/*.json`。舊版 `.kiro.hook` 與 Manual hook 教學可能已過時。

File Save：SQL 語意審查

{
  "version": "v1",
  "hooks": [
    {
      "name": "supabase-sql-review",
      "description": "Review saved Supabase SQL.",
      "trigger": "PostFileSave",
      "matcher": "^supabase/migrations/.*\\.sql$",
      "action": {
        "type": "agent",
        "prompt": "Review migration safety, RLS coverage, tenant isolation, unsafe privileges, destructive changes, indexes and rollback implications. Report blockers first. Do not modify the file automatically."
      },
      "enabled": true
    }
  ]
}

Agent Stop：最終品質門檻

{
  "version": "v1",
  "hooks": [
    {
      "name": "supabase-final-review",
      "description": "Review Supabase changes before stop.",
      "trigger": "Stop",
      "action": {
        "type": "agent",
        "prompt": "If Supabase-related files changed, verify versioned migrations, RLS, tenant isolation, server-only secrets, updated types, tests and disclosure of destructive operations. If unrelated, take no action."
      },
      "enabled": true
    }
  ]
}
取捨：lint、test、secret scan 用 command hook；RLS 語意與 migration 風險用 agent hook。不要把所有品質檢查都丟給 Agent。
07 · Practice

三個由淺入深的練習任務

Level 1｜建立 profiles table

要求 Kiro 建立 `profiles` migration，關聯 `auth.users`，並加入基本 SELECT / UPDATE RLS。

觀察：是否載入 migrations + RLS steering？是否區分 USING 與 WITH CHECK？

Level 2｜建立多租戶 project_members

建立 organizations、projects、project_members，僅允許同組織成員存取。

觀察：是否避免只以前端 organization_id 控制？是否測試跨租戶拒絕？

Level 3｜Realtime 任務看板

在多租戶資料模型上加入任務更新訂閱、重連、取消訂閱與 optimistic update reconciliation。

觀察：是否同時啟動 RLS + Realtime steering，又沒有重複或衝突指令？
