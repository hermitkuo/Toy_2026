醫療資料去識別化流程：台灣醫院 AI／研究資料治理版

從「移除姓名」升級為「目的分流、風險量化、金鑰分離、退出權、稽核日誌、週期重評」的可稽核證據鏈。

一句話結論

醫療資料去識別化不是「AES 加密＋移除姓名」。台灣醫院真正需要的是一套能被 IRB、法遵、主管機關與訴訟檢驗的證據鏈。

最大盲點

假名化不等於匿名化。若同一權責者同時掌握分析資料與還原對照表，技術上仍可識別；這不是充分去識別化。

1. 起點：先判斷「目的內」還是「目的外利用」

這是整條流程是否啟動的第一個分歧。臨床照護本身需要識別病人；研究、模型訓練、跨院合作則通常進入目的外利用，必須建立去識別化與治理證據。

使用場景法源定位去識別化策略
醫師調閱病人 eGFR、透析紀錄、用藥歷程做即時決策原始蒐集目的內利用不去識別。用 RBAC、最小權限、break-glass、稽核日誌控管。
用歷史透析資料訓練 IDH、住院、死亡、CKD progression 模型特定目的外利用去識別化或取得同意／IRB 核准；需能自證「無從識別特定當事人」。
跨院合作、對外驗證、公開資料集、產學合作目的外利用＋第三方傳輸最高強度治理：DUA、退出權、稽核、禁止再識別，必要時使用合成資料或差分隱私。
設計原則：照護端不要為了形式合規硬做去識別化；訓練端、研究端、對外端則不能只靠加密與遮蔽姓名。

2. HIPAA 與台灣個資法的本質差異

面向HIPAA台灣個資法／醫療資料治理
去識別化標準Safe Harbor 移除 18 類識別碼，或 Expert Determination。原則式：「無從識別特定當事人」；實務上需自建風險證據。
可操作性checklist 明確。需要工程、統計、法遵共同定義風險門檻。
中間態Limited Data Set＋DUA。無完全等價制度；多以 IRB、DUA、資料安全措施補強。
健康資料二次利用研究授權、IRB waiver、de-identification。受個資法、人體研究法、醫療法、憲判 13、健保資料專法共同影響。

台灣端的工程缺口是：不能只拿 HIPAA Safe Harbor 當清單打勾，而要能提出「欄位分級、手法選擇、風險量化、過程驗證、稽核追蹤」的本地化證據。

3. 法源分流：三種資料來源，不要混在同一套治理邏輯

資料來源主要法源／治理框架治理重點
院內自有病歷、檢驗、透析、門診資料個資法、人體研究法、醫療法、IRB目的外利用判斷、去識別化、IRB、資料使用協議、稽核。
健保資料庫全民健康保險資料管理條例申請審查、退出權、指定安全作業環境、結果不得含可識別個人資料、成果回報、銷毀義務。
生物檢體、基因體、多組學資料人體生物資料庫管理條例、IRB、同意書同意、退出、檢體與資料分離、基因資料再識別風險、長期保存治理。

4. 六階段去識別化資料管道

0

盤點分級

標記直接識別碼、準識別碼、敏感屬性、中性欄位，產出資料字典與欄位風險表。

1

直接識別碼處理

移除或假名化病歷號、身分證、姓名、聯絡方式；使用 HMAC token 與金鑰分離。

2

準識別碼一般化

年齡分層、日期偏移、地理上捲、罕見組合併，降低外部連結攻擊。

3

敏感與稀有值處理

罕病、極端值、特殊病程做 top/bottom coding、ICD 併類或 outlier suppression。

4

風險量化

計算 k-anonymity、l-diversity、t-closeness、全域與局部重識別風險。

5

擾動／合成資料

對外釋出或跨院合作時使用差分隱私、合成資料或統計結果輸出限制。

階段 6 是橫切層：治理、驗證、退出權、稽核與週期重評必須覆蓋前述所有階段。

5. 風險量化：不要只說「已去識別」

建議在 R 端使用 sdcMicro，Python pipeline 則可整合 ARX 或自建 k-anonymity 檢查。核心不是套件，而是留下可重跑、可稽核、可比較版本差異的風險報告。

R：sdcMicro 概念範例

library(sdcMicro)

sdc <- createSdcObj(
  dat = dialysis_df,
  keyVars = c("age_band", "sex", "county", "hd_start_year"),
  sensibleVar = "primary_diagnosis"
)

kAnon(sdc)
sdc <- localSuppression(sdc, k = 5,
                        importance = c(1,1,2,2))
sdc@risk$global$risk

Python：快速 k-anon 稽核

qi = ["age_band", "sex", "county", "hd_start_year"]
group_sizes = df.groupby(qi).size()
violations = group_sizes[group_sizes < 5]
risk_pct = df.set_index(qi).index.isin(
    violations.index
).mean()
print(f"低於 k=5 的高風險紀錄佔比: {risk_pct:.2%}")

6. 階段 6：治理層才是最容易被查核的部分

階段 6 不應被寫成「完成去識別化」的勾選欄位，而應拆成七個各自留下證據鏈的控制點。

6.1 金鑰託管分離vault／analytics 權限分離、HSM/KMS、雙人授權。
6.2 無從識別自證報告欄位分級、技術手法、k/l/t 值、抑制率、外部連結測試。
6.3 過程驗證系統SOP、版本控管、執行紀錄、異常處理。
6.4 資料使用協議 DUA禁止再識別、轉授權、超目的利用、違約處理。
6.5 退出權註記opt-out flag、釋出快照、排除筆數、時點雜湊。
6.6 稽核日誌append-only log、hash chain、WORM 封存。
6.7 週期性重評季度重評、motivated intruder test、重評觸發條件。

7. 台灣可採用的驗證與標準框架

標準／框架用途
CNS 29100／29100-2隱私與去識別化過程管理系統基礎。
PIDIPMS把去識別化做成可驗證的管理系統，而非一次性資料清洗。
ISO/IEC 20889對照 generalization、suppression、perturbation 等技術與攻擊風險。
ISO 25237健康資訊假名化與身分保護原則。
sdcMicro／ARX實作 k-anonymity、l-diversity、t-closeness、風險量化。
保守假設：通過過程驗證不代表資料必然脫離個資法適用；仍須視去識別化後是否已達無從直接或間接識別特定個人。

8. 對 Nephro Copilot 的落地架構

系統層資料性質建議治理方式
閘門一：確定性規則／臨床即時決策目的內照護資料不去識別；用 RBAC、break-glass、最小權限、操作稽核。
閘門二：LightGBM／tabular ML 訓練歷史資料、目的外利用完整六階段流程；model card 記錄資料版本、k 值、抑制率、欄位處理規則。
閘門三：LLM 自然語言層可能重述病人細節或從 context 重建個資輸出端 PHI filter、prompt log 去識別化、禁止 pseudo_id 回填、RAG context 最小化。
對外驗證／投稿資料第三方或跨院使用優先使用統計結果、合成資料或高強度去識別資料；搭配 DUA 與輸出審查。
健保資料研究法定特殊資料來源依健保資料專法申請、審查、指定環境、退出權、成果不得可識別、銷毀義務處理。

最高槓桿做法

把階段 6 做成 governance.SKILL.md，讓每個新研究專案啟動時，自動產出欄位分級表、去識別化參數表、風險報告、opt-out 過濾紀錄、DUA 範本、稽核 log schema、model card 資料治理段落、IRB／法遵送審附件包。

9. Not-to-do：高風險或不值得投入的方向

只移除姓名、身分證、病歷號準識別碼仍可與外部資料連結，例如年齡、地區、罕病、日期、特殊治療事件。
把 AES 加密當成去識別化加密是存取控制，不是去識別化；若同一權責者可解密，仍可識別。
將假名化資料直接視為匿名資料假名化仍可能透過對照資訊還原，需分權與稽核。
保留所有精確日期與地理資訊對 longitudinal model 有幫助，但重識別風險高；應改用日期偏移、相對時間、區域上捲。
把一次性資料清洗當成合規完成外部資料環境會變，需週期性重評。
在 LLM prompt 或 log 中保留原始 PHI會形成第二份未治理資料庫，且更難追蹤與刪除。
對臨床照護即時資料硬做去識別化會破壞臨床可用性；照護場景應用權限與稽核，不是去識別化。

10. 最終判斷

對台灣醫療 AI 專案而言，去識別化的核心不是「資料有沒有看起來匿名」，而是能否對每一批目的外資料完整回答四個問題：

問題應有證據
為什麼這批資料可以被使用？目的分流、IRB、法源依據、DUA。
哪些欄位可能識別病人，如何處理？欄位分級表、去識別化轉換規則。
處理後的重新識別風險是多少，如何證明？k/l/t 報告、抑制率、motivated intruder test。
若被查核，能否提出完整證據鏈？金鑰分離、退出權、稽核日誌、重評紀錄。

落地結論：照護端不去識別但嚴格授權；訓練端完整去識別並量化風險；對外驗證端優先輸出統計結果、合成資料或高保護去識別資料；健保資料另走專法流程。

本頁為技術治理與專案設計整理，非法律意見。實際送審前，仍應由院內法遵、IRB、資安與熟悉個資法／醫療資料法制的法律顧問共同確認。
