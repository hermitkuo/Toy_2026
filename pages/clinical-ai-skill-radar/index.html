首波建議啟動的 6 個 Radar

先建立能直接支撐目前臨床 AI、資料與研究專案的最小組合。

1. Clinical Research研究問題、證據缺口與設計
2. Data Analysis清理、建模與可重現分析
3. Biomedical InformaticsFHIR、OMOP、Terminology
4. Agentic Workflow工具調用、HITL、狀態與審計
5. Clinical AI Evaluation品質、安全、漂移與偏差
6. UI / Visualization臨床判斷、介面與交付

建議追蹤頻率

頻率應依技術變化速度與判斷成本設定，而不是所有 Radar 都每週更新。

Radar建議頻率判斷理由
UI Skill Radar每週社群驅動、變化快、專案多
Agentic Workflow每週Framework、tool calling 與 Agent pattern 更新快速
Data Analysis每兩週工具多，但真正有價值的變化沒有那麼頻繁
Clinical Research每兩週需要方法學審查，不能只追數量
Clinical AI Evaluation每兩週LLM 與 Agent 評測生態正快速成長
Biomedical Informatics每月標準相對穩定，重點在實作與驗證能力
Governance & Safety每月需要精準判斷，不適合新聞式更新
PM／Leadership每月價值來自工作流整合，不是短期熱度

所有 Radar 的固定輸出模板

每次更新都使用同一結構，才能比較、淘汰與形成長期決策紀錄。

訊號

本期新增、升溫、降溫與停止維護的 Skills。

可用性

是否真實可安裝、支援哪些 Agent、是否可重現。

工作流價值

能替代多少人工步驟與 Prompt 迭代。

差異化

與既有 Skills 的重複度、衝突與互補關係。

導入成本

安裝、整合、維護、學習與治理成本。

決策

安裝、測試、觀察、淘汰，並清楚說明理由。

Not-to-do

避免 Radar 退化成沒有決策價值的工具新聞摘要。

不要做「所有 AI Skills Radar」

範圍過廣，最後只會變成資訊流，無法連接到任何具體工作流與採購判斷。

不要按供應商分類

Claude、Codex、Gemini 只是執行環境。真正需要管理的是臨床研究、資料分析與治理能力。

不要讓熱度主導

Stars 與 X 討論最多只占 10%。若不能改善交付、降低風險或節省迭代，就不值得導入。
